Day 20 – Alembic Migrations (Database Version Control)

Today you'll learn how professional teams manage database schema changes without manually running SQL scripts.

This is heavily used in:

FastAPI Projects
Microservices
Banking Applications
GenAI/RAG Platforms
Why Alembic?

Without Alembic:

Developer A:
CREATE TABLE customers

Developer B:
ALTER TABLE customers
ADD phone_number

Developer C:
ALTER TABLE customers
ADD address

Chaos occurs when moving code across environments.

Alembic provides:

Database Version Control

similar to:

Git for Database Schema

Session 2 (11 AM – 1 PM)
Configure env.py

Import Base metadata.

from database.database import Base

Replace:

target_metadata = None

with:

target_metadata = Base.metadata

Import all models:

from models.customer import Customer
from models.account import Account
Create First Migration
alembic revision --autogenerate -m "create customers table"

Generated file:

alembic/versions/

xxxxxxxx_create_customers_table.py

Example:

def upgrade():

    op.create_table(
        "customers",

        sa.Column(
            "id",
            sa.Integer(),
            primary_key=True
        ),

        sa.Column(
            "name",
            sa.String()
        )
    )
Apply Migration
alembic upgrade head

Verify:

SELECT *
FROM customers;
Session 3 (4 PM – 6 PM)
Modify Existing Table

Suppose we add:

phone_number = Column(
    String
)

to Customer model.

Generate Migration

alembic revision --autogenerate -m "add phone column"

Generated:

def upgrade():

    op.add_column(
        "customers",

        sa.Column(
            "phone_number",
            sa.String()
        )
    )

Apply:

alembic upgrade head
Downgrade

Rollback one migration:

alembic downgrade -1

Rollback specific version:

alembic downgrade
abc12345
Check Migration History
alembic history

Current Version

alembic current

Common Mistakes
Mistake 1

Using:

Base.metadata.create_all()

in production.

Why bad?

No version tracking
Mistake 2

Editing migration files manually without review.

Mistake 3

Running migration directly on production.

Always test in:

Dev
QA
UAT
Production
FastAPI Startup Integration

Avoid:

Base.metadata.create_all(
    bind=engine
)

once Alembic is adopted.

Use migrations instead.

Interview Questions
What is Alembic?

Database migration tool for SQLAlchemy.

Why use Alembic?

Version control for database schema changes.

Difference between create_all() and Alembic?

create_all():

Creates tables
No version tracking

Alembic:

Tracks schema changes
Supports rollback
What is Migration?

A database schema change.

What is upgrade()?

Applies changes.

What is downgrade()?

Rolls back changes.

Why use autogenerate?

Detect model changes automatically.

Can autogenerate detect everything?

No.

Review migration file before applying.

What is head?

Latest migration version.

What table does Alembic create?
alembic_version

Tracks current DB version.
